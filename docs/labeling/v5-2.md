# Trucksafe Labeler v5.2: Rear-Assembly Prompt Recovery + Lock-Jaws Spatial Prior

> **Goal:** Two small targeted changes on top of v5.1, both validated against the same 90-image audit set, with the aim of clearing v5.2 to scale on the full ~7,500 archive.
>
> **What's NOT changing:** describe-not-judge architecture, inspection-level schema reframing (v5), manufacturer-aware side_view fields (v5), Gemma 4 31B AWQ-4bit serving stack, vLLM endpoint, cropping for fifth_wheel and pintle_hook (unchanged from v5.1), all out-of-scope items from v5.

---

## Two changes

### Change 1: rear_assembly prompt rewording

**Problem:** `safety_pin_visible == true` peaked at 30/30 in v4, dropped to 17/30 in v5 (schema reframing introduced new presence/absence fields that diluted attention), partially recovered to 24/30 in v5.1 (prompt reordering helped). Target: ≥28/30, matching v3's pre-reframing baseline. Pin visibility is the highest-signal pintle_hook field for failure detection and the one we most need to get right before scaling.

**Approach:** further prompt tightening on rear_assembly. Don't change the schema. Don't add fields. Move toward:

- Lead the prompt's body (after any system framing) with the safety-pin question, *before* any other rear-assembly fields. The model's first observation pass should be "is the pin visible," not "describe the hook." v5.1's reordering moved in this direction; push it further.
- Add explicit anti-default-to-false language, the same intervention that fixed v2 → v3 (0/30 → 28/30). The v5 reframing diluted this. Restore the language exactly: something like "Do not default to reporting the safety pin as absent. Look for a small cylindrical pin or bolt protruding through the latch mechanism, often horizontal. If you can see any part of such a pin, report it as visible."
- Optionally: add one annotated reference example showing a clearly-visible safety pin from uncle's archive (you should already have suitable exemplars from v3-era labels). Few-shot multimodal worked for the manufacturer taxonomy; same principle here.

The agent has license to iterate the prompt once on the audit set to hit ≥28. If two iterations don't hit it, stop and surface.

### Change 2: lock_jaws_underneath fixed-band crop

**Problem:** `fifth_wheel_variant` mechanism identification was 2/30 (7%) in v5.1 vs the 60% success bar — a hard fail. Diagnosed cause: archive lock_jaws photos are taken from underneath with the phone pointing up, producing predictable composition where the mechanism occupies a horizontal band in the upper portion of the frame. The rest of the image (ground, suspension, asphalt, mud flaps) is irrelevant context that the labeler is also "seeing." v4's per-image detection failed on this category (37% localization, 4.4% median crop area — too tight when it did work). A simpler deterministic preprocessor exploits the spatial regularity.

**Approach:** before sending a lock_jaws_underneath image to the describe pass, crop to a **fixed horizontal band: image rows 20% to 70% (top-to-bottom), full width**. This is hardcoded, no detection inference. The crop is wider than v4's tight box and is sized to capture the locking mechanism plus the surrounding plate context that disambiguates two-jaw vs single-bar.

**Implementation:**
- Add a `fixed_band_crop` preprocessing step in the v5.2 runner, applied only when `evidence_type == "lock_jaws_underneath"`.
- Save the cropped image to `audit-batch-05/lock_jaws/crops/{image_id}.jpg` for HTML review.
- Record `localization: {strategy: "fixed_band", band_rows: [0.20, 0.70]}` in the output JSON so the comparison report can show that this category uses a different preprocessing path than fifth_wheel (per-image detection) or pintle_hook (per-image detection).

**Prompt tweak to pair with the crop:** add a spatial-prior sentence near the top of the lock_jaws_underneath prompt: "The locking mechanism in this image appears as a horizontal band just below the top edge of the fifth-wheel plate. Two-jaw mechanisms appear as a pair of curved metal fingers wrapping a central kingpin. Single-bar mechanisms appear as a horizontal bar positioned in front of the kingpin. Focus your description on this region."

## Success bars (both must pass to recommend scale-up)

1. **`safety_pin_visible == true` ≥ 28/30** (recovery from 24 → 28+).
2. **`fifth_wheel_variant` non-`unclear` ≥ 18/30** (the 60% bar that v5.1 failed at 2/30).

Plus the regression check:

3. **No regression on v5.1's wins.** Manufacturer ID engagement holds at ≥18/30 (60%), sub-object consistency holds at 30/30, Jost honest-unknown rate holds at >75%. If any of these regress meaningfully, the prompt changes have an unintended side effect and need investigation before scale-up.

If success bars 1 and 2 both pass and there's no v5.1 regression, the recommendation is: **scale v5.2 to 7,500 archive images**.

If success bar 1 passes but 2 fails, recommendation is: **scale partial — fifth_wheel and pintle_hook on v5.2, lock_jaws deferred pending the `fifth_wheel_overview` evidence type** (3-4ft framing) discussed in v5.1 follow-up. The schema reframing accepts lock_jaws as optional confirmation evidence; we don't have to block the whole pipeline on it.

If neither passes, stop and surface.

## Stop-and-ask thresholds

- If the rear_assembly prompt iteration doesn't recover safety_pin_visible to ≥28 in two attempts — stop, don't iterate further.
- If the 20-70% fixed band visibly misses the mechanism on >5/30 lock_jaws spot-checks — stop, the band needs tuning and that's a separate decision.
- If v5.2 introduces unexpected regression on side_view manufacturer fields — stop, the rear_assembly prompt changes shouldn't affect side_view but if they do, something structural is wrong.
