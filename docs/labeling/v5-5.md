# Trucksafe Labeler v5.5: Category Self-Check Field + Pintle Chain Schema Relaxation

> **Goals (two changes, both small):**
> 1. Add a single top-level field, `photo_matches_category`, to every evidence type's describe schema. The model self-reports whether the input image actually shows the hardware its source folder claims it does. This lets us filter out miscategorized images from training without manual review.
> 2. Relax the `safety_chains_clipped_to_bar` field on `rear_assembly` to count "at least one chain visibly clipped" as the engagement-confirmed state, matching uncle's actual inspection workflow. Most pintle photos in the archive are taken from a side angle that shows one chain clearly; the second is typically out of frame. Uncle's existing approved-positive workflow accepts these photos as pass, so the schema must too — otherwise the model would be trained to disagree with the verdicts attached to its own training data.
>
> **Scope:** Audit run on the same 90-image set only. Scale-up to 7,500 is a separate decision after seeing v5.5 audit results.
>
> **What's NOT changing:** describe-not-judge architecture, inspection-level schema reframing (v5), manufacturer-aware side_view fields (v5), few-shot multimodal references (v5.4), pintle simplified schema (v5.4) *except for the chains-clipped field*, fixed-band crop for lock_jaws, per-image detection crop for fifth_wheel and pintle_hook, Gemma 4 31B AWQ-4bit serving stack, vLLM endpoint.

---

## The change

Add `photo_matches_category` as a top-level field to all three describe-only schemas:

```json
"photo_matches_category": "yes" | "no" | "unclear"
```

Field semantics:
- `yes` — the image clearly shows the hardware corresponding to the `evidence_type` (e.g., a `side_view` evidence type with a side view of a fifth-wheel coupling).
- `no` — the image clearly shows something else (different hardware, different angle, unrelated subject, blurry-beyond-recognition).
- `unclear` — the image is ambiguous or partial — could be the right hardware but the model can't confidently confirm.

The field is **independent of inspection content**. A photo can be `photo_matches_category: yes` and still be unevaluable for inspection (poor lighting, occluded mechanism). A photo can be `photo_matches_category: no` even if it shows valid truck hardware that just isn't the category. Don't conflate this with `image_quality`.

---

## Why this works

The audit results across v3–v5.4 have repeatedly surfaced "miscategorized image" as the root cause for individual label oddities — chain-to-bracket close-ups in the pintle_hook category, lunette-only shots tagged as pintle inspection photos, etc. The model has *already* been correctly identifying that these photos don't show the expected hardware (it just had no field to report it in, so the signal showed up as `not_visible` or unrelated descriptions in `factual_summary`).

This field makes that latent signal explicit. The model doesn't need to learn anything new; it needs a slot to write the observation it's already making.

## Schema changes

**Change 1: Add `photo_matches_category` to all describe schemas.**

Update three describe-only schema files:

- `shared/schemas/fifth_wheel_coupling_describe_only.json` — add `photo_matches_category` as required top-level field.
- `shared/schemas/pintle_hook_describe_only.json` — add `photo_matches_category` as required top-level field.

The production schemas (non-describe-only variants) also gain the field for consistency — the runner doesn't strip it from the assembled output, since downstream training data assembly needs it to filter.

**Change 2: Relax `safety_chains_clipped_to_bar` in `rear_assembly`.**

Replace the v5.4 enum:

```json
// OLD (v5.4):
"safety_chains_clipped_to_bar": "both_clipped" | "one_clipped" | "neither_clipped" | "unclear" | "not_visible"

// NEW (v5.5):
"safety_chains_clipped_to_bar": "at_least_one_clipped" | "none_clipped" | "unclear" | "not_visible"
```

Rationale: most pintle photos are taken from a side angle that shows one chain prominently; the second is typically off-frame. Uncle's existing approved-positive workflow accepts these photos as pass, so the schema's engagement-confirmed state must match. The field semantics become:

- `at_least_one_clipped` — the model can see at least one safety chain clipped to the bottom bar with a metal clip. The far-side chain may or may not be visible. This is the engagement-confirmed state.
- `none_clipped` — chain(s) visible but none are clipped to the bar.
- `unclear` — chain(s) and bar partially visible, can't confirm clipping.
- `not_visible` — chains and/or bar are out of frame entirely.

Update both `shared/schemas/pintle_hook.json` and `pintle_hook_describe_only.json` to reflect this enum.

**Important: this is a workflow-honesty change, not a permissiveness change.** The model is being aligned with what uncle's inspection actually verifies, given the photographic limitations of typical driver shots. The model is not learning to ignore unclipped chains — it still reports `none_clipped` when it sees that — it's learning to accept side-angle shots that confirm at least one chain clipped as evidence the inspection passed (because that's what uncle accepts).

## Prompt integration

Add a short instruction near the top of each evidence type's prompt, before the few-shot reference block:

> "Before describing the image, first determine whether it actually shows [the relevant hardware for this evidence type]. Set `photo_matches_category` to:
> - `yes` if the image clearly shows [the hardware];
> - `no` if it shows something else entirely (different hardware, wrong angle, unrelated subject, severely blurred);
> - `unclear` if you can see hardware that might be relevant but you can't confidently confirm.
>
> If `photo_matches_category` is `no` or `unclear`, still complete the rest of the schema as best you can — fill remaining fields with `not_visible` where appropriate, and use `factual_summary` to describe what the image actually shows."

Per evidence type, [the relevant hardware] becomes:
- `side_view`: "a side view of a fifth-wheel coupling, showing the trailer apron resting on the fifth-wheel plate"
- `lock_jaws_underneath`: "an underneath view of fifth-wheel locking jaws engaging a kingpin"
- `rear_assembly`: "a view of a pintle hook coupling, including the hook itself and the safety chains"

The instruction is short on purpose. The model has already shown (across earlier audits) that it can recognize when a photo doesn't match the category — it just needs to be told to report it.

## Comparison report

`comparison_v5_4_v5_5.md` in `audit-batch-07/`. The headline question this report answers: **how many of the 90 audit images are miscategorized, per the model's self-check?**

Structure:

1. **Miscategorization breakdown:**
   - Per source folder (fifth_wheel, lock_jaws, pintle_hook), counts of `photo_matches_category` values (yes / no / unclear).
   - Total `no` and `unclear` images across all 90.
   - Per `no`/`unclear` image: the model's `factual_summary` (what the image *does* show, per the model).
   - **Spot-check by human:** the user reviews the model-flagged miscategorizations in the HTML reviewer and confirms or overrides. Report which the model got right vs got wrong on the miscategorization call itself.

2. **Re-baselined metrics (v5.4 numbers, recomputed excluding `photo_matches_category != yes` images):**
   - Manufacturer ID rate, both raw (v5.4: 27/30) and re-baselined (27/n where n excludes miscategorized side_view images).
   - Lock_jaws variant ID rate, raw (v5.4: 12/30) and re-baselined.
   - Pintle joint-pass count under the **new v5.5 criterion**: `hitch_latch_state == "closed"` AND `safety_chains_count >= 1` AND `safety_chains_clipped_to_bar == "at_least_one_clipped"`. Compare against v5.4's strict criterion (`both_clipped`) where v5.4 hit 8/30 — expect the new criterion to land much higher (22+ given the original analysis that most v5.4 failures were second-chain-out-of-frame). Re-baseline both the raw v5.5 count and the count excluding miscategorized images.
   - Holland engagement metrics, re-baselined.

   The expectation is most metrics shift modestly upward — miscategorized images were dragging numbers down with `not_visible` / `unclear` answers on the inspection-relevant fields.

3. **Direct comparison v5.4 → v5.5 on yes-only images:**
   - For images that are `yes` in both v5.4 (implicitly — v5.4 didn't have the field) and v5.5, do the inspection-field calls match? They should — v5.5 is v5.4 plus one field, no other prompt changes.
   - Any unexpected drift on the inspection fields is a flag that the new instruction is interfering with the existing prompt structure.

4. **Schema integrity:** 90/90 still validates against the updated describe-only schemas.

5. **Elapsed time:** Expect <5% increase over v5.4. The new field is small and the prompt addition is short.

6. **HTML reviewer:** extend the v5.4 reviewer at `:8770/labels/audit-batch-07/review.html`. Add a filter/toggle to show only `photo_matches_category != yes` images at the top of the page — that's the cohort the user spot-checks.

## Success criteria

The experiment is **informational**. Outcomes:

- **Clean signal (expected):** model flags 5-15 miscategorized images out of 90, the user agrees with most of them on spot-check, and re-baselined v5.4 metrics shift modestly upward. → **Proceed to scale-up decision with v5.5 schema.** v5.5 is the version that goes to the full 7,500.

- **Over-flagging:** model flags >25 images as miscategorized, many of which look fine on spot-check. → The prompt addition is being too aggressive. Iterate the threshold language ("clearly shows" is doing work here — may need tightening).

- **Under-flagging:** model flags <3 images, but the user can find 5+ clear miscategorizations on manual review. → The instruction isn't landing. Iterate the prompt with a few-shot example of a miscategorized image (you have at least 3 candidates already identified).

- **Schema breakage:** integrity drops below 90/90 after adding the field. → Stop. Something's wrong with prompt assembly or schema validation.

---

## Stop-and-ask thresholds

- Schema integrity < 90/90 → stop, surface.
- Inspection-field drift on `photo_matches_category: yes` images > 10% from v5.4 → stop, surface. The new field shouldn't change how the model answers the other fields on photos that match the category. If it does, the instruction is bleeding into other reasoning.
- Elapsed time more than +20% over v5.4 → stop, discuss.

## Implementation order

1. Update describe-only schema files with `photo_matches_category` as a required top-level enum field.
2. Update production schema files (non-describe-only) with the same field.
3. Update `pintle_hook.json` and `pintle_hook_describe_only.json` with the relaxed `safety_chains_clipped_to_bar` enum (`at_least_one_clipped` | `none_clipped` | `unclear` | `not_visible`). Old enum values (`both_clipped`, `one_clipped`, `neither_clipped`) must not appear anywhere in the schemas.
4. Update Pydantic models (`schemas.py` or equivalent) to match both schema changes.
5. Update the rear_assembly prompt to use the new chains-clipped language. Specifically: "Report `at_least_one_clipped` if you can see at least one safety chain visibly clipped onto the bottom bar with a metal clip. Side-angle photos typically show one chain clearly; the far-side chain may be out of frame, and this is acceptable for the inspection."
6. **User updates `assets/few_shot_examples/captions.json` pintle entries** to match the new semantics — caption should describe what's visible without confabulating both chains. Example: "Hitch latch fully closed around the lunette ring. At least one safety chain visibly clipped to the bottom bar with a metal clip (side-angle framing — far-side chain may be off-frame)." **If captions still reference `both_clipped` or describe both chains when the image shows one, the few-shot signal will conflict with the new schema.**
7. Update the rear_assembly, side_view, and lock_jaws_underneath prompts with the new `photo_matches_category` instruction block before the few-shot references.
8. **Probe run on 3 images first** — one per source category. Verify both new fields validate, verify `photo_matches_category` matches a human read on each, verify `safety_chains_clipped_to_bar` correctly reports `at_least_one_clipped` on a typical side-angle pintle photo. 60 seconds of work. Don't skip.
9. If probe is clean, run full 90.
10. Generate comparison report + HTML reviewer with the new filter toggle.
11. User reviews the flagged miscategorizations and tags each as agree/disagree. Update the report with the agreement count.
